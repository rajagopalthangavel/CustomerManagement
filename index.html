Overview

Small teams often keep customer details in spreadsheets, which makes it hard to control who can change records and easy to end up with duplicates. I built this app as a personal project to provide one place where an admin manages staff accounts and the team maintains a clean, searchable list of customers.

I designed and built the whole stack myself: the data model, the Go API, the MongoDB integration and the Angular front end.

What it does

  • Role-based loginUsers sign in with email, password and role. The API checks each one and returns a clear reason when a login fails.
  • User managementAn admin can create, view, edit and delete staff accounts. A default admin account is created on first start so the app is usable straight away.
  • Customer recordsFull create, read, update and delete for customers, including name, email, area, city, postcode and phone number.
  • Paginated tablesUsers and customers appear in Angular Material tables with pagination, so the lists stay usable as data grows.
  • Safe deletesA confirmation dialog appears before any record is removed.
  • No duplicatesUnique indexes on email in both collections stop the same person being added twice, enforced at the database level.
  • Readable IDsRecords get prefixed IDs, such as CUST- and USER-, so their type is obvious in logs and support conversations.

API design

The API exposes one route per operation, grouped by resource. Every response uses a shared envelope with a result, an error message and a verification flag, so the front end handles success and failure the same way everywhere.

Key decisions

Go for the API

Go’s standard HTTP server and gorilla/mux gave me a fast, dependency-light API that compiles to a single binary, which keeps deployment simple.

MongoDB with an embedded address

Customer addresses are stored as an embedded document instead of a separate table, because they’re always read with the customer. This keeps reads to a single query.

A generic data-access layer

The db package uses Go reflection to pick the right collection from the type of the struct passed in, so the same insert, find, update and delete helpers serve both users and customers.

Lazy-loaded Angular modules

The user and customer features load only when visited, which keeps the initial download small and the code split along clear feature lines.

Configuration outside the code

The port, database URL and database name live in a JSON file loaded with Viper, so the same build runs locally or on a server without code changes.

What I’d build next

This version focuses on the core workflow. To make it production-ready, these are the next steps I’ve planned:

  1. Stronger security. Hash passwords with bcrypt and issue JWTs on login, attaching them through the HTTP interceptor that’s already in the Angular app.
  2. Validation and HTTP semantics. Validate input on the server and map routes to REST verbs, for example GET /customers and PUT /customers/{id}.
  3. Tests. Unit tests for the Go services and component tests for the Angular forms.
  4. Search and filtering on the customer table.
  5. Docker and a live demo. A Docker Compose setup for the API, UI and database, deployed so anyone can try it.
